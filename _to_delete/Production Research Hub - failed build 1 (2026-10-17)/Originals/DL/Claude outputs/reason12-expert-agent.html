Reason 12 · Architecture recommendation

Reason 12 Expert Agent

One knowledge package, mounted in both Hermes and Claude, built from today's manual extraction.

Don't make a model ingest the manual. Build a skill that knows exactly where in the manual to look, and looks in one step. That is what a know-it-all actually is, and it's the only version that can cite a page number.

The corpus we produced today is 2.8 MB — 385,496 words, roughly 510,000 tokens across 1,466 manual pages. Nothing memorizes that. Sonnet's window is 200k; a local model in Hermes is typically 32k–128k. Even if it fit, paying half a million tokens to answer "what does Kbd Track do on Subtractor's Osc 1" is absurd when the answer lives on page 862.

The good news is the research turned up something that collapses this from two builds into one: Hermes Agent is compatible with the agentskills.io open standard — the same SKILL.md format Claude uses. Hermes reads skills from ~/.hermes/skills/ and can also scan external skill directories. So one folder, symlinked twice, serves both.

The three layers

Progressive disclosure: the agent pays for what it opens, nothing else.

~100 tok

Always loaded. Just the skill's name and description, sitting in the system prompt so the agent knows Reason knowledge exists and when to reach for it.

~5k tok

Loaded when triggered. SKILL.md — the router. All 54 devices with one line each on what they're for, the CV and audio routing rules, your house rules, and the map of where every detail lives. Most questions get answered from here without opening another file.

0 until read

Opened on demand. One reference file per device and per operations topic, plus a grep script for exact parameter lookup. Sitting on disk costs nothing.

Router + the two files a real question needs~15,000 tokens

Same scale. That ratio is the entire argument.

Why not the other three options

ApproachVerdictReason
Fine-tune a model No Costs real money, can't cite pages, invents plausible-but-wrong parameter values, goes stale on the next Reason update, and you'd redo it for every model you switch to.
Stuff the whole manual in No 510k tokens exceeds every window you'd realistically run, and burns the budget on every question regardless of how narrow it is.
Vector RAG Not here Needs embedding infrastructure in both places, chunk boundaries slice parameter tables in half, and fuzzy similarity is worse than exact match when the query is a literal control name.
Agent Skill + grep Yes Zero infrastructure, exact matching on real parameter names, page-cited answers, and the same folder runs in Hermes and Claude unchanged.

Vector search earns its keep on messy, unstructured, constantly-growing corpora. This one is fixed, clean, and already has a table of contents — the conditions where retrieval-by-navigation wins.

This isn't just my judgment call

A May 2026 paper — Is Grep All You Need? How Agent Harnesses Reshape Agentic Search — compared grep against vector retrieval across four agent harnesses including Claude Code. Finding: grep generally yielded higher accuracy than vector retrieval. Independent write-ups of similar tests put vector-over-chunks around 60% against roughly 68% for an agent iterating with grep, find and cat.

The second finding matters more for you

The same paper found scores "depend strongly on which harness and tool-calling style is used, even when the underlying conversation data are the same." Identical skill, identical corpus, different agent — different accuracy. That is a direct prediction about Hermes versus Claude, and it changes the build: run the evals in both harnesses, not once. Whatever gap shows up is the real cost of running this locally, measured instead of guessed.

The honest counterweight: LlamaIndex's position is that lexical search is fast and precise but degrades at enterprise scale, where hybrid wins. At 2.8 MB across 80-odd files, this corpus is nowhere near that ceiling — it sits squarely in grep's sweet spot. If the library later grows to include every Rack Extension manual and years of your own session notes, revisit it then.

The folder

├── reference/

│   ├── devices/              # 54 files, one per device — not one per chapter
│   │   ├── subtractor.md     #   ch34, pp. 857–882
│   │   ├── thor.md           #   ch33, pp. 817–856
│   │   └── …
│   ├── operations/           # sequencer, mixer, routing, sampling, Remote…
│   └── tables/               # key commands, menu reference
├── data/
│   ├── devices.json          # today's manifest — machine-readable
│   ├── device-images.json    # front/back panel URLs
│   └── device-params.json    # ← from `reason code`: 3,700+ canonical names
└── scripts/

You already own the missing piece

Your reason code project has device_params.json — canonical parameter names for 46 devices, 3,700+ of them, pulled by scan_rack.py straight out of Reason's own Remote map files. That is the authoritative vocabulary: exactly what Reason calls each control, which is exactly what grep needs to match. It's a better index than anything derivable from the manual prose, and it partly closes the vocabulary-mismatch problem below. Copy it in.

One file per device, not per chapter

The manual's chapters are a book's structure. Chapter 62 alone is nine separate devices (COMP-01 through UN-16) in one file; chapter 5 is 178 KB, about 45k tokens, too big to open whole. The agent's structure should be one file per thing you'd ask about. Average chapter is ~10k tokens — fine to read entire; the four oversized ones get split by topic.

Every file keeps its page range

So answers land as "Filter 1 tracks the keyboard at 0–100% via Kbd Track — manual p. 869" and you can verify it in ten seconds. Same evidence discipline you use everywhere else.

Mounting it in both places

Canonical folder lives once. Symlink into each host — the same pattern already running between reason code and Homeroom Studio.

~/.reason_voice/reason12_manual/reason12-expert/     # source of truth

ln -s …/reason12-expert  ~/.hermes/skills/reason12-expert
ln -s …/reason12-expert  ~/reason\ code/.claude/skills/reason12-expert

Edit in one place, both agents see it. Hermes will also self-improve the skill during use, which writes back to the same folder — Claude picks that up for free.

Optional refinement on the Claude side: wrap it in a reason12-expert subagent so deep manual dives happen in an isolated context and don't crowd out whatever you're actually building. Hermes has the equivalent with its isolated subagents.

Build order

  1. Write ten eval questions first, with answers you've confirmed in the manual. Run them against a bare agent and record what it gets wrong. Anthropic's own guidance is explicit about this: evals before documentation, or you end up writing for imagined failures instead of real ones.

  2. Split the corpus into per-device and per-topic files. Scripted from what's already extracted — the chapter boundaries and page ranges are done.

  3. Write 00-index.md: topic → file → page map, plus a synonym table so "pumping" and "ducking" route to sidechain compression and CV.

  4. Write SKILL.md: the 54-device roster, routing rules, your stock-devices-first rule and the no-analogies rule, and the file map. Directive rather than open-ended, so a smaller local model in Hermes can still follow it.

  5. Add lookup.py — deterministic grep returning snippet plus chapter and page. Runs without loading its own source into context.

  6. Re-run the evals in both harnesses — Claude and Hermes — and compare against the step-1 baseline. Same skill, same corpus, two numbers. The research says they will differ; the gap between them is the measured price of running local.

  7. Mount, then iterate from observed failures — where it opens the wrong file, what it never opens at all. Log the fixes in DECISIONS.md.

Steps 2–5 are about an hour, because the hard part — a clean, complete, page-accurate extraction — is already sitting in ~/.reason_voice/reason12_manual/.

Where this will let you down

Vocabulary mismatch

Grep finds "sidechain"; it does not find "pumping." The synonym table in the index covers the common cases, but you'll keep finding gaps for months. Add them as you hit them — that's the self-improving loop earning its keep.

Small local models use skills worse

If Hermes is pointed at a 36B local model, expect it to skip references and read the wrong file more often than Claude does. Writing SKILL.md directively helps. If accuracy matters more than running local, point Hermes at a frontier model for this skill specifically.

The manual only knows stock Reason 12.7

No Rack Extensions, no VST specifics, and parameter drift against whatever 12.x you're running. The agent will be confidently wrong about any RE you own unless the skill says plainly that REs are outside its knowledge.

It can't see the panels

The front/back images are URLs. A text agent reasons about the panel from the manual's words, not from looking at it. Fine for parameters; weak for "which knob is top-left."

Someone already built one — worth looking at

simontho/reason-remote-gen is a Claude skill that generates Reason Remote Maps and Lua Codecs for hardware controllers. Two reasons it matters here.

It validates the structure. Its layout is the pattern above, arrived at independently: SKILL.md plus a references/ tree holding format docs, 33 exported device Remote Info files, and real-world example maps and codecs. Same shape, same reasoning.

It also happens to solve your Launchkey problem. The README's own first example is "generate a remote map for the Novation Launchkey controlling Thor" — which is the pad-and-knob mapping you've been fighting on the 49 MK3. It handles Rack Extensions and VSTs too, via Reason's Remote Info export, which patches the biggest hole in a manual-only skill.

Caveats, plainly: five stars, five commits, one author, MIT-licensed, tested on Reason 13 rather than 12. Read the SKILL.md before installing anything that writes files into your Reason config — same rule Anthropic gives for third-party skills. Treat it as a template and a useful separate tool, not a dependency.

One architectural call worth making now

Keep the recipe book as a separate, sibling skill. The manual is static and verifiable — Reason Studios' word, citable to a page. Your recipes are opinionated, tested by ear, and still evolving. Merging them makes it impossible for the agent — or you, six months from now — to tell which is which. Two skills that reference each other keeps the provenance clean and lets the recipe skill cite the manual skill the way your recipes already cite tested signal flow.
